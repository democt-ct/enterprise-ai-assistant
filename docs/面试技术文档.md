## 一、系统总览

### ⭐ 一句话概括

⭐ 一个 **多 Agent 协作的企业智能助手**：Orchestrator 四级路由（寒暄 → 关键词 → 上下文 → LLM 兜底），HR/IT/法务/财务四个领域 Agent 各管一摊，RAG 混合检索 + 工具调用双驱动，Review Agent 做幻觉审查后流式输出；底层由 Planner + 工作流引擎、三层记忆、安全网关、可观测性与评测体系支撑。

### 几块，各管一摊

| 模块 | 一句话职责 |
|------|-----------|
| ⭐ **Orchestrator** | 四级路由：寒暄正则 → 关键词 → 短应答上下文 → LLM 兜底，输出 primary/secondary、意图（query/action）、置信度 |
| ⭐ **BaseAgent (ReAct)** | 领域通用骨架：RAG 检索 → 构造 prompt → 工具调用循环（query 轻量 / action 完整双模式）→ 最终回答 |
| ⭐ **RAG 检索层** | FAQ 快速路径 → LLM 查询改写 → 向量 (Chroma+BGE) + BM25 → RRF 融合 → 可选 Cross-Encoder 重排 → 结果缓存 |
| ⭐ **Tool Agent** | 统一工具执行入口：参数净化（防越权）→ 权限校验（角色/scope）→ 审计日志 → 执行 |
| ⭐ **Review Agent** | 规则确定性检查 + LLM 兜底审查，防数值错误、制度编造、错误透传 |
| ⭐ **三层记忆** | L1 内存滑动窗口（5 轮）→ L2 SQLite 会话持久化（7 天 TTL）→ L3 长期语义记忆（偏好/事实） |
| ⭐ **Planner** | LLM 拆解多意图为 DAG → Kahn 拓扑排序 |
| **Workflow Engine** | 按拓扑序分批并发执行 DAG 节点，超时/重试/失败降级，task_state 落库 |
| **审批状态机 + 事件总线** | FSM 严格校验状态流转（非法转换直接抛错）+ 发布/订阅解耦业务事件 |
| **Protocol** | Agent 间交割协议：结构化上下文（摘要 + 未解决项）、多专家结果 LLM 合并 |
| **Gateway** | JWT 双 Token（access 8h + refresh 7d 可撤销）、登录锁定、Token Bucket 限流、PBKDF2 60 万次哈希、输入净化 |
| **Skills 层** | 原子工具之上的复合业务能力：审批引擎、工单生命周期、通知中心、报表 |
| **Observability** | 每请求 TraceCollector → 按日 JSONL；SSE 逐步事件；检索元数据 |
| ⭐ **Evaluation** | 37 用例 golden set：路由/工具/检索三项准确率 + 平均耗时/Token |

## 二、核心链路

### 一条请求从头走到尾

```
用户输入 "帮我查一下年假还剩几天，顺便提交一个请假申请"
     │
     ▼
① 路由：关键词命中 "年假"+"请假"+"申请" → hr_agent, intent=action,
   confidence=0.92（纯规则，0 token）
     │
     ▼
② Planner 检测双意图 → 拆为 DAG：[t1 查余额] → [t2 提交请假]
     │
     ▼
③ WorkflowEngine 按拓扑序执行：t1 就绪先跑（无依赖的节点可批量并发）
     │
     ▼
④ t1 执行：RAG 检索 HR 制度 → DeepSeek 生成 → tool_call get_leave_balance
     │
     ▼
⑤ t2 执行：tool_call submit_leave_request → 审批流创建
   （状态机 draft→pending）+ 事件总线通知审批人
     │
     ▼
⑥ Tool Agent 对每个工具调用做权限校验 + 审计落库
     │
     ▼
⑦ Review Agent 审查：核对回答中的年假天数与工具结果一致 → 通过
     │
     ▼
⑧ SSE 逐事件推送：routing → retrieval → tool_call → reasoning → answer → done
```

### 完整延迟时间线（实测典型值）

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 寒暄/关键词路由 | 0-2ms | 纯内存正则匹配，不调 LLM |
| LLM 路由 | 200-600ms | DeepSeek，temperature=0.0，JSON 模式 + Pydantic 校验 |
| Embedding 生成 | 30-80ms | 本地 BGE-large-zh-v1.5，1024 维 |
| 向量检索 | 5-15ms | ChromaDB 本地持久化索引 |
| BM25 检索 | 2-5ms | 内存索引，jieba 分词 |
| RRF 融合 | <1ms | 纯数学运算 |
| 重排序（可选） | 50-200ms | BGE Cross-Encoder 本地推理，默认关闭 |
| DeepSeek 首 token | 400-1200ms | 含 reasoning（开启 thinking 时更长） |
| 工具调用往返 | 100-500ms/次 | SQLite 本地查询，WAL 模式 |
| Review（规则层） | 1-5ms | 纯正则 + 字符串匹配 |
| Review（LLM 兜底） | 300-800ms | 仅边界情况触发 |
| **总计（单 Agent 简单查询）** | **~1.0-2.5s** | 路由 + RAG + 1 次 LLM |
| **总计（Action + 工具调用）** | **~2.0-5.0s** | 含 2-3 轮工具调用 |
| **Quick Tool 快速路径** | **~50ms** | 高频查询路由后直接调工具，零 LLM、零 token |

## 三、模块逐个说

### 3.1 Orchestrator — 四级路由

**概念**：将用户输入路由到正确的领域 Agent，同时分类意图是 "查询" 还是 "操作"。真实实现是 **四级**：寒暄正则 → 关键词匹配 → 短应答上下文推断 → LLM 兜底。

**为什么这么设计**：纯 LLM 路由有三个致命问题——慢（每次 500ms+）、贵（消耗 token）、不确定（temperature 再低也可能随机漂移）。核心哲学是 ⭐ **"确定性优先，LLM 兜底"**：能用规则解决的问题绝不用模型。

**好处**：
- ⭐ 关键词层命中即返回，0 token 消耗。路由专项评测 20 例中 16 例由关键词层命中（80%），整体准确率 95%
- 关键词匹配是确定性的，同一问题不会两次路由到不同 Agent
- 支持否定句检测（"不需要请假" 不会误路由到 HR）
- 多领域命中时的消歧规则：命中数差异 ≥2 倍信任规则层；差异小则按关键词位置先后决定主领域
- 第四层 "短应答上下文推断"：用户说 "好的""可以" 时，从最近一轮 assistant 引导语推断路由，不需要 LLM

**不这样的坏处**：⭐ 如果纯 LLM 路由，每条消息先烧 300-800 token 做分类。月活 1000 用户 × 日均 20 条 × 30 天 = 60 万条消息/月，就是 **1.8 亿–4.8 亿 token/月的纯浪费**。且用户说 "帮我查一下" 时，LLM 可能猜错领域。

### 3.2 BaseAgent — ReAct 循环骨架

**概念**：每个领域 Agent 共享的推理-行动循环：检索知识 → 理解意图 → 调用工具 → 获得反馈 → 继续推理 → 最终回答。

**为什么这么设计**：手写 ReAct 循环而非用 CrewAI/AutoGen 等框架。框架会引入三个问题——黑箱调度（你不知道为什么 Agent 某次没调工具）、token 浪费（隐式 prompt）、难以裁剪（框架假设的 Agent 角色和我们的企业场景不匹配）。

**好处**：
- 完全掌控循环的每一步：何时调工具、何时停、超时怎么办
- ⭐ **query / action 双模式**：query 走单轮低温（temperature=0.1、top_k=3、不注入工具描述）；action 走完整 ReAct（temperature=0.5、top_k=10、注入工具）。查询类任务不为不需要的能力付钱
- ⭐ **工具调用上限按置信度分档**：confidence ≥0.9 → 2 轮；0.7-0.9 → 3 轮；<0.7 → 5 轮
- 30 秒硬超时保护；达到上限强制生成最终回答（status=partial，不静默失败）
- LLM 输出做了确定性兜底：工具参数 JSON 解析失败用空参并校验、DeepSeek thinking 的 reasoning_content 正确回传（DeepSeek 要求必须回传，否则报错）

**不这样的坏处**：用 CrewAI 意味着你把调度权交给了一个无法调试的黑箱，面试官追问 "你的 Agent 为什么在第 3 轮调了错误的工具" 时你无法回答。

### 3.3 RAG 检索层 — 混合检索 + RRF 融合

**概念**：FAQ 快速路径 → LLM 查询改写 → 向量检索（Chroma + BGE）与 BM25 检索并行 → RRF 融合 → 可选重排 → 结果缓存。

**为什么这么设计**：⭐ 两种检索方式互补——向量检索擅长 "意思相近"（"怎么请假" ≈ "休假申请流程"），BM25 擅长精确匹配（"产假天数" 一定能找到含这个词的文档）。RRF 只看排名不看绝对分数，天然鲁棒，不需要调融合权重（k=60 是业内经验值）。

**好处**：
- ⭐ **FAQ 快速路径**：纯查询类短问题（<30 字）直接 BM25 匹配，跳过 LLM 改写和向量检索，进一步降本
- **查询改写**：LLM 把口语化问题改写为检索友好 query；改写失败回退原文，不阻塞主流程
- ⭐ **RRF 融合**：BM25 权重 1.5 倍——企业制度文档中精确关键词（条款名、专有名词）优先级高于语义近似
- **结果缓存**：内存 dict（TTL 60s、maxsize 256），60 秒内相同查询跳过 embedding 和向量检索
- **索引热更新**：watchdog 监听 docs 目录，2 秒防抖自动重建索引；启动时 `is_index_stale()` 自检（mtime + 文件数量比对），无需手动维护
- 重排序默认关闭，仅在需要极致精确时开启（`RERANK_ENABLED`）

**不这样的坏处**：只用向量检索 → "产假" 可能被语义相近的 "陪产假" 淹没；只用 BM25 → 用户问 "怎么休息" 永远找不到含 "请假流程" 的文档。没有改写 → "年假还剩几天，怎么请" 这类混合 query 检索效果差。

### 3.4 Review Agent — 幻觉防御

**概念**：⭐ 在回答返回给用户之前做双重审查——先规则（快、确定性、零 token），再 LLM（慢、只兜边界情况）。

**为什么这么设计**：幻觉是 RAG + LLM 系统的头号敌人。规则层做四类确定性检查：
1. **数值一致性**：回答中的 "年假 X 天" 必须与工具返回一致
2. **空回答/过短检查**：<10 字直接判失败
3. **错误透传检查**：工具返回 error 但回答没体现 → 判为问题
4. **制度溯源检查**：回答引用 "§3.1""第5.2条" 时，必须在检索片段中找到原文

LLM 层只在边界情况触发：有 warning 但无硬伤，或置信度在灰色区间（0.6-0.9）。低置信（<0.7）回答自动加 "仅供参考" 前缀。

**好处**：
- ⭐ 绝大多数检查由规则层完成，零 token 消耗
- 双层防御：规则抓到硬伤直接拦下，规则不确定的交给 LLM 二次判断
- 审查异常只记 warning 不阻断回答——审查器本身不能成为可用性故障点

**不这样的坏处**：没有审查 → 一次幻觉可能导致用户在 HR 系统里按错误天数提交请假，是真实的企业损失。只做 LLM 审查 → 每条回答多烧 500-1000 token，成本翻倍。

### 3.5 三层记忆架构

**概念**：L1 工作记忆（内存滑动窗口 5 轮）→ L2 会话持久化（SQLite，7 天 TTL）→ L3 长期记忆（SQLite 表，提取用户事实和偏好）。

**为什么这么设计**：不同记忆有不同的生命周期和访问模式。L1 追求快（纯内存）但有容量限制；L2 让会话跨进程重启不丢失；L3 跨会话累积用户画像（"张三是 HR 部门的经理"）。三层分开存储而非全部塞进上下文窗口，避免 prompt 膨胀。

**好处**：
- L1 提供毫秒级对话连贯性
- L2 让用户刷新页面后继续之前的对话
- L3 提取偏好（如 "张三总是申请年假"）用于个性化回答，`recall_as_context` 按 user_id 注入
- ⭐ **长会话压缩**：L2 消息数 ≥20（约 10 轮）时，后台线程异步生成 100-200 字摘要，删除旧消息、保留最近 6 条，防止上下文无限膨胀

**不这样的坏处**：只有 L1 → 刷新页面对话丢失。全部塞进 LLM 上下文 → prompt 越来越长，token 消耗增长，超出窗口后前面的信息被截断。

### 3.6 Planner + Workflow Engine — DAG 任务分解与执行

**概念**：用户一句话包含多个意图时（"查一下年假再帮我请个假"），Planner 用 LLM 拆解为有依赖关系的子任务 DAG，Kahn 算法拓扑排序后交给 WorkflowEngine 执行。

**为什么这么设计**：Planner 是 ⭐ **"LLM 做计划，确定性引擎做执行"** 的分层设计——LLM 负责理解语义（需要智能），拓扑排序与调度是确定性代码（Kahn 算法不可能排错）。

**好处**：
- **按依赖分批并发**：每轮找出所有依赖已满足的就绪节点，批量并行执行；单节点批次直接执行，省去线程开销。严格意义上不是纯串行——"查余额" 和 "查制度" 这类无依赖任务会同时跑
- **死锁检测**：pending 但无就绪节点 → 记录并跳过，不会挂死
- 节点失败重试 1 次 → 仍失败则标记 workflow failed，回答中体现错误
- task_state 落库，工作流进度可查询
- Planner 可整体开关（`PLANNER_ENABLED`），简单场景不浪费 token；LLM 拆解失败自动回退单任务
- ⭐ **审批状态机 FSM**：请假记录严格按 `draft → pending → approved → completed / rejected / cancelled` 流转，非法转换直接抛 `InvalidStateTransition`；审批步骤 `pending → approved / rejected / skipped`
- **事件总线**：`approval.completed`、`leave.submitted`、`workflow.failed` 等事件发布/订阅，审批完成自动通知审批人

**不这样的坏处**：没有 Planner → "帮我查年假然后请假" 只能完成第一步，打断对话流。让 LLM 直接决定执行顺序 → 可能把 "提交请假" 排在 "查余额" 前面。

### 3.7 Protocol — 跨 Agent 交割

**概念**：当一个 Agent 处理完后，把上下文（摘要、未解决项、用户画像）打包交给下一个 Agent 继续处理。

**为什么这么设计**：企业场景一个问题常跨越多个领域（"去上海出差三天，顺便看看那边的合同合规"）。交割协议的关键是 ⭐ **结构化上下文传递**：不是把整个对话历史丢过去，而是抽取摘要 + 未解决项。

**好处**：
- 两种交割模式：路由侧识别 secondary Agent（**并行执行**，ThreadPoolExecutor）+ Agent 自身建议转交（串行接力，携带 handoff_context）
- LLM 综合多个 Agent 的回答消除重复矛盾；LLM 综合失败回退分隔线拼接，不丢内容
- 用户上下文（user_id、部门、角色）在路由后才注入，避免污染关键词匹配

**不这样的坏处**：不支持交割 → 跨域问题是用户痛点。简单拼接两个 Agent 回答 → 两个 Agent 都说 "建议联系 XX 部门" 的冗余。

### 3.8 Tool Agent — 统一工具执行（权限 + 审计）

**概念**：所有 Agent 的工具调用统一走 Tool Agent 入口，四步：参数净化 → 权限校验 → 审计落库 → 执行。

**为什么这么设计**：⭐ LLM 是 **不可信的参数来源**——prompt injection、幻觉都可能让 LLM 生成越权参数。安全边界必须放在确定性代码里，而不是祈祷模型 "守规矩"。

**好处**：
- ⭐ **参数净化**：非 admin 角色强制把 `user_id` 类参数覆盖为当前登录用户，防止 LLM 篡改 user_id 越权查他人数据
- **审批人防伪造**：`approver_id` 参数必须等于当前用户（除非 hr/admin），防止 LLM 伪造审批人身份
- **权限模型**：ToolDef 声明 `{roles, scope}`（self/department/tenant），角色不匹配或越 scope 直接拒绝并返回明确错误
- **审计**：每次工具调用写入 `audit_log`（谁、何时、调了什么工具、参数、耗时、成功与否），满足企业合规要求

**不这样的坏处**：直接在 Agent 里调工具 → LLM 说 "帮我查一下张三的工资" 就可能真的查出别人数据，这在企业内部是不可接受的。

### 3.9 Skills 复合业务层

**概念**：在原子工具之上组合出完整业务能力：通用审批引擎（多级审批链）、工单生命周期（创建→处理→完成→关闭/重开/升级）、通知中心、聚合报表。

**为什么这么设计**：⭐ 复杂业务流程（如审批链规则）写进 LLM prompt 既不稳定也不可审计。审批链按请假天数确定：≤3 天直属上级；>3 天加部门负责人；>7 天加 HR——这是业务规则，由确定性代码保证，LLM 只负责触发。

**好处**：
- 状态流转由 FSM + 代码保证，可测试、可审计
- Skills 可独立运行（CLI/定时任务），不依赖 Agent 也能跑
- 报表能力（工单日报/周报、请假月报、预算使用率）直接服务管理场景

## 四、工程化与可观测性

### 4.1 熔断器为什么用、不用会怎样

LLM API 可能因上游限流、欠费、网络抖动短暂不可用。熔断器（5 次失败 → 断路 60s → 半开探测）防止 API 不可用时持续发请求，并允许服务自动恢复。重试策略：仅对可重试错误（timeout/429/5xx/连接错误）触发指数退避重试（1s → 2s → 4s，最多 3 次），业务性错误直接透传。

**不用会怎样**：⭐ API 挂了，每个请求仍然等待超时（可能 30s），瞬间堆积上千等待线程，内存耗尽。熔断后调用在 <1ms 内快速失败，保护自身和上游。

### 4.2 缓存策略：缓存什么、为什么不缓存什么

**缓存了什么**：RAG 查询结果（内存 dict，TTL 60s，maxsize 256）。企业知识库不频繁变动，60 秒内相同查询跳过 embedding 和向量检索。

**为什么不缓存 LLM 回答**：⭐ 同一问题问张三和李四答案不同（余额、部门、角色不同）。缓存 LLM 回答会导致串数据，是安全风险而非性能问题。

**为什么 Embedding 不需要缓存**：BGE 模型（~1.3GB）通过双重检查锁单例常驻内存，本身就等价于最贵的缓存。

### 4.3 并发控制：几层、各保护什么

| 层级 | 机制 | 保护什么 |
|------|------|----------|
| L1 请求限流 | Token Bucket，per-user 10 req/min + per-IP 30 req/min | 防止单个用户或 IP 打满服务 |
| L2 数据库 | SQLite WAL + busy_timeout + threading.local() 每线程连接 | 读写不互斥，避免 SQLite 并发瓶颈 |
| L3 LLM 调用 | 熔断器 + 指数退避重试（3 次） | API 故障时快速失败，不堆积线程 |
| L4 知识库构建 | Embedder 双重检查锁 | BGE 模型 1.3GB 只加载一次 |
| L5 Trace 写入 | 每请求独立 TraceCollector，单行 JSON 原子追加，失败不冒泡 | 可观测性写入永远不拖垮业务 |

### 4.4 安全纵深

| 层 | 机制 |
|----|------|
| 认证 | JWT access token（8h）+ refresh token（7d，sha256 落库可撤销，登出/改密码可吊销全部） |
| 登录防护 | 连续失败 5 次锁定 15 分钟；密码 PBKDF2-SHA256 60 万次迭代 + 常量时间比较；旧明文哈希登录时自动迁移 |
| 输入净化 | Unicode NFKC 正规化（防同形字攻击）、控制字符剔除、长度截断、ID 格式正则校验 |
| 会话隔离 | session 所有权映射：他人 session_id 访问自动重开新会话 |
| ⭐ 工具权限 | 角色 + scope 校验 + 强制绑定 user_id/approver_id（防 prompt injection 越权） |
| 生产校验 | `APP_ENV=production` 启动即校验 JWT_SECRET（禁用默认值）与 LLM_API_KEY，缺省拒绝启动 |

### 4.5 可观测性

- **Trace**：每个 HTTP 请求注入独立 TraceCollector，事件（routing / retrieval / tool_call / llm_call / answer / error）按日写入 `traces/trace_YYYY-MM-DD.jsonl`，单行 JSON 原子追加
- ⭐ **SSE 全链路回放**：推送给前端的每个事件（routing → retrieval → tool_call → reasoning → answer）同步写入 trace，一次请求可完整回放定位问题
- **检索元数据**：每次查询记录 cache_hit、rewritten_query、vector_count、bm25_count、fusion_method、rerank_used——检索调优不用猜
- **服务就绪状态**：后台初始化期间 `/api/health` 返回 `initializing` + 进度，`/api/chat` 返回 503；初始化异常写入 init_progress.error，避免 daemon 线程静默死亡

### 4.6 评测体系

- **Golden set**：37 条用例（hr 10 / it 7 / legal 7 / finance 6 / cross 4 / fallback 3），覆盖路由、工具调用、检索来源
- **三项指标**：路由准确率（expected_agent 比对）、工具准确率（expected_tools 子集比对）、检索准确率（expected_sources 命中比对）
- **快速模式**：`retrieval_only=True` 只跑路由 + 检索，不调 Agent，可在 CI 中快速回归
- ⭐ **实测数据**（37 用例最近一次全量报告）：路由准确率 86.5%、工具准确率 100%、检索准确率 82.1%、平均耗时 3.3s；路由专项 20 例准确率 95%（其中 16 例由零 token 的关键词层命中）

### 4.7 启动优化

三轮优化历程：⭐ 同步阻塞初始化（首屏 8-15s）→ 后台线程 + 懒加载（首屏 2s，但首条查询要等 BGE 加载 2-5s）→ **后台初始化 + Embedding 预加载（首屏 2s + 首条查询即时）**。

关键决策：
- FastAPI lifespan 立即 yield，初始化跑 daemon 线程，就绪前友好降级（503 + 进度）
- BGE 1.3GB 模型显式预热，避免首查等待
- 4 个知识库**串行**加载——ChromaDB 底层 SQLite 不支持多个 PersistentClient 并发访问同一目录（真实踩过的坑）

### 4.8 其他面试亮点

⭐ **intent 分类带来差异化执行**：query 意图（查余额）走轻量路径——单轮低温回答、不注入工具、轻量审查；action 意图（提交请假）走完整 ReAct + 工具调用 + 完整 Review。本质是 **不为不需要的能力付出成本**。

⭐ **操作卡片（Action Card）**：用户说 "我想请假" 时，Agent 返回结构化表单定义（字段、类型、下拉选项），前端动态渲染交互卡片。比在聊天框打字填表单优雅，也减少 "开始日期是？结束日期是？" 的无效追问。

⭐ **快速工具路径（Quick Tool）**：高频查询（"我的年假还剩多少"）声明 `quick_triggers` 后，路由阶段直接调工具返回结果，完全跳过 LLM——一个查询从 1.5s 降到 ~50ms，零 token。

⭐ **LLM 提供商热切换**：所有模块通过统一 `get_client()` 工厂获取 OpenAI 兼容客户端，换模型只需改三个环境变量（LLM_API_KEY / LLM_BASE_URL / LLM_MODEL），不碰业务代码。今天连 DeepSeek，明天可以连 Qwen 或 SenseNova。

## 五、失败降级哲学

⭐ 每一层都默认 "我可能会挂"，挂了之后要有确定性的下一步，而不是把异常抛给用户：

| 环节 | 降级链 |
|------|--------|
| 路由 | 寒暄 → 关键词 → 上下文 → LLM → 校验失败重试一次 → fallback |
| 查询改写 | LLM 改写失败 → 原文检索 |
| RAG | 检索异常 → 空结果，prompt 引导 Agent 明说无法回答 |
| 重排 | 模型加载/调用失败 → 保持原序 |
| 流式输出 | SSE 流式异常 → 非流式回退 |
| Planner | LLM 拆解失败 → 单任务透传 |
| 快速工具 | 参数构建/执行异常 → 回退完整 ReAct |
| 多专家合并 | LLM 综合失败 → 分隔线拼接 |
| 工具执行 | Tool Agent 不可用 → 直接调用（权限入口保留） |
| 审查 | Review Agent 异常 → 只记 warning，不阻断回答 |
| 服务初始化 | 后台线程异常 → init_progress.error + 503 友好提示 |

## 六、面试追问速答

| 追问 | 回答 |
|------|------|
| ⭐ **为什么不用 LangChain？** | LangChain 抽象层太厚，调试困难。手写 ReAct 循环每个分支自己控制，出了问题能定位到具体行。 |
| **为什么不用 CrewAI？** | CrewAI 的 Agent 调度是黑箱，不适合需要确定性的企业场景。我的 Orchestrator 关键词匹配规则是 100% 可解释的。 |
| ⭐ **为什么用 RRF 而不是加权求和做融合？** | 向量分数和 BM25 分数量纲不同，加权求和需要调超参且泛化差。RRF 只看排名不看分数绝对值，天然鲁棒。 |
| **为什么重排序默认关闭？** | Cross-Encoder 每次推理 50-200ms，绝大多数场景 top_k=10 的检索质量已足够。只在需要极致精确时按需开启。 |
| **为什么用 SQLite 而不是 PostgreSQL？** | 单机部署的企业内部工具，SQLite WAL 支持并发读，零运维。换 PostgreSQL 只需改连接字符串，架构不阻塞。 |
| **为什么记忆要分三层？** | 不同记忆的生命周期和访问模式不同。混在一起要么 prompt 太长（成本高），要么丢得太快（体验差）。 |
| **为什么 Planner 用拓扑排序而不是让 LLM 决定顺序？** | LLM 可能在排序上出错（把 "提交请假" 放 "查余额" 前面）。Kahn 算法是确定性的，不可能排错。 |
| **为什么 embedding 选 BGE 而不是 OpenAI text-embedding？** | BGE-large-zh-v1.5 中文检索效果强，且本地部署零延迟、零费用、数据不出企业内网。 |
| **工具调用上限为什么按置信度分档？** | 置信度高说明路由没错，2 轮够；低可能路由偏了，多给几轮让 Agent 纠正。避免一刀切。 |
| ⭐ **这个系统最大的工程挑战是什么？** | 在 "确定性规则" 和 "LLM 智能" 之间找平衡。每加一个 LLM 环节就多一次不确定性，我的策略是能用规则就不用模型。 |
| ⭐ **如何防止 LLM 篡改参数越权？** | 双保险：Tool Agent 对 user_id 类参数强制绑定登录用户，approver_id 必须等于当前用户；权限校验在确定性代码里，LLM 只负责 "想"，不负责 "信"。 |
| ⭐ **怎么证明系统好用而不是自说自话？** | 37 用例 golden set 持续回归，路由/工具/检索三项准确率 + 耗时/token 指标；trace 可逐请求回放。 |
| ⭐ **最大的坑是什么？** | 三个：LLM JSON 输出不稳定（Pydantic 校验 + 重试）；BGE 1.3GB 模型加载慢（预加载 + 双重检查锁）；Chroma 不支持并发 PersistentClient（4 个 KB 串行加载）。 |
| ⭐ **为什么不缓存 LLM 回答？** | 回答依赖用户上下文（余额、部门、角色），缓存会串数据，安全风险大于性能收益。 |
| ⭐ **query 和 action 为什么分开？** | 查询任务不需要工具和重审查，走轻量路径省 token 降延迟。这是 "不为不需要的能力付钱" 的工程化表达。 |
| **怎么处理长对话？** | L1 窗口 + L2 持久化 + 消息数 ≥20 时后台异步压缩为摘要、保留最近 6 条，防止 context 无限膨胀。 |
| **Agent 回答错了怎么办？** | Review Agent 规则层核对数值/溯源，LLM 层兜底，低置信加 "仅供参考"；工具错误必须体现在回答中（错误透传检查）。 |
| **Planner 是串行执行吗？** | 不是。WorkflowEngine 按拓扑序分批执行，无依赖的就绪节点并发跑；只有依赖链上的节点严格串行。 |
